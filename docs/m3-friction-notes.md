# M3 마찰 완화 — 설계·구현 노트

> 작성: 2026-08-04 | 브랜치 `feature/m3-friction` | 결정: D15(승인 채널)·D16(압축 확인)

## 요약

M2 제거의 근본 원인은 승인 게이트의 **채널**과 **적용 범위** 둘 다였다. M3는 승인을
AskUserQuestion 선택창으로 전환하고(D15), 발산 0인 요청은 명세 제시와 승인을 선택창
하나로 합쳐 왕복 1회·클릭 1번으로 줄였다(D16). 훅 3종이 공통 함수로 선택 결과를
판독하므로, M2에서 반복된 "승인이 인식되지 않는" 계열의 데드락이 구조적으로 사라진다.

## 사용자 교정 (2026-08-04, M2 dogfooding 직후)

다른 프로젝트 실사용에서 사용자가 강하게 교정한 두 가지:

1. **"선택지 질문"은 처음부터 AskUserQuestion UI를 의미했다.** 명세를 텍스트로 제시하고
   채팅에 '승인'을 타이핑하게 하는 흐름은 설계 의도가 아니었다. 실제로 사용자가 '승인'을
   직접 입력했는데도 게이트가 풀리지 않는 판정 실패까지 겹쳤다.
2. **명시적 지시에 승인을 되묻는 것은 목적 전도다.** "학습 돌려"처럼 의도가 이미 명확한
   지시에 명세·승인 왕복을 요구했다. 도구의 목적은 Claude가 의도를 *정확히 파악*하게
   하는 것이지, 사용자에게 확인 절차를 강요하는 것이 아니다.

## 실측 근거 — 선택창 결과는 훅이 읽을 수 있다

M2 HANDOFF에는 "AskUserQuestion 선택지로 고른 답은 도구 결과라 게이트가 읽지 못한다"고
기록돼 있었으나, **이 전제는 틀렸다**. 실제 세션 트랜스크립트(.jsonl)를 확인한 결과:

- 선택창 응답은 `type: "user"` 항목의 `toolUseResult`에 **구조화되어** 남는다:
  `toolUseResult.questions[]` (질문 원문·옵션)와 `toolUseResult.answers` (질문→답변 맵).
- 사용자가 옵션 대신 직접 입력한 자유 텍스트도 같은 `answers` 맵으로 들어온다.
- 도구 결과는 다음 어시스턴트 턴 이전에 기록되므로, 승인 클릭 → 다음 도구 호출 시점에는
  트랜스크립트에서 안정적으로 판독된다 (Stop 훅의 당해-턴 레이스와 다른 지점).

따라서 새 훅 등록 없이 기존 3계층이 트랜스크립트 판독만으로 선택 승인을 인식할 수 있다.

## 구현

### 승인 판정 (`filter.ts` → `isAskApproval`)

- 후행 괄호 장식만 제거(`"승인 (권장)"` → `"승인"`) 후 **전체 일치**를 요구한다.
- 부분 일치를 쓰지 않는 이유(실제 사례): 옵션 라벨 *안에* '승인'이 포함될 수 있다 —
  `"발산 0이면 통과 + 비가역만 항상 승인 (권장)"`은 승인이 아니다.
- 기존 NEGATION 가드 유지: 자유 입력 `"아니 승인 말고…"`는 승인이 아니다.

### 판독·전이 (`common.ts` → `findAskApproval` / `resolveAskApproval`)

- 뒤에서부터 스캔해 **가장 최근 선택창 하나만** 판정한다 — 승인은 마지막에 화면에 보인
  질문에만 성립(C3와 같은 원칙). 그 이전 선택창의 '승인'은 보지 않는다.
- `cycleStartedAt` 이전 타임스탬프의 결과는 무시 — 이전 사이클 승인 누수 방지.
- 전이 시 아카이브: 본문 `[MR-SPEC]` 명세가 있으면 그것을, 없으면(압축 확인 경로)
  질문·답변 자체를 명세로 보존한다(D13 유지).
- **훅 3종이 모두 호출한다**: pre-tool-use(클릭 직후 첫 쓰기), stop(읽기만 하는 작업의
  정상 종료), prompt-submit(다음 발화). 어느 경로가 먼저 오든 같은 전이 — 한 훅만 보다가
  생기는 데드락 계열을 구조적으로 차단.

### 프로토콜 개정 (`protocol.ts` 6·7항)

- 승인은 반드시 선택창으로: 선택지 `"승인"`(정확히 이 라벨) + `"수정 필요"`.
- 발산 0: question 텍스트가 `[MR-SPEC]`로 시작하는 재진술 하나로 명세+승인을 합친다.
  이미 명시된 내용은 되묻지 않는다.
- 발산 >0: 기존대로 본문 명세를 제시하되 같은 턴에 선택창으로 승인을 받는다(D14 —
  명세가 화면에 보이는 상태에서 선택).
- 비가역 작업은 "알아서 해" 신호에도 확인 필수(D16).
- 채팅 '승인' 입력은 백업 경로로 유지 — 종료 판정자는 사용자(D9)라는 원칙 그대로.

### 계측

`approved` 이벤트에 `via: "ask" | "prompt"` 필드 추가 — 채널 전환 후 텍스트 승인이
실제로 사라지는지 dogfooding에서 관찰한다.

## 코드 리뷰 반영 (2026-08-04, Code Reviewer 에이전트 — 실측 프로브 기반)

critical 0건, major 5건 전부 반영, minor 7건 중 3건 반영:

- **M1 모양 위조**: 판정 조건이 결과의 "모양"뿐이었다 → `isSidechain` 배제, `answers` 배열 배제, `questions` 비어 있음 배제. **후속 과제**: tool_use_id를 역추적해 실제 AskUserQuestion 호출에 바인딩하는 완전한 검증.
- **M2 타임스탬프 fail-open**: 타임스탬프 없는 항목이 사이클 경계 검사를 건너뛰었다 → `cycleStartedAt`이 있으면 타임스탬프 없는 승인은 무효 (fail-closed).
- **M3 무관 질문의 '승인' 라벨**: 라벨은 모델이 작성하므로, 아무 질문에나 '승인' 라벨을 달아 클릭 한 번으로 게이트를 여는 경로가 있었다 → **승인은 명세에만 성립한다**: 질문 텍스트에 [MR-SPEC](압축 확인) 또는 사이클 내 본문 명세가 있을 때만 인정. 모델이 마커를 빠뜨리면 승인 클릭이 무효가 되는 마찰이 생길 수 있으나, 게이트 무력화보다 낫다고 판단(채팅 '승인' 백업 경로가 탈출구). 채팅 '승인'은 D9 원칙대로 제한 없음.
- **M4 조건부 승인**: 괄호 제거가 부정 가드보다 먼저라 "승인 (수정 후에)"가 승인됐다 → 부정 가드를 원문에 먼저 적용.
- **M5 거부된 명세 바인딩**: 본문 명세를 우선해서, 거부된 구버전이 아카이브·해시에 바인딩될 수 있었다 → 압축 확인([MR-SPEC] 질문)으로 승인되면 그 질문·답변을 우선 아카이브.
- **m2**: `resolveAskApproval`의 상태 저장 실패가 pre-tool-use의 fail-closed를 타고 읽기 도구까지 막을 수 있었다 → 저장 실패를 삼키고 메모리 판정 반환(다음 훅이 재판정).
- **m3**: 스캔 창 60→200 항목(병렬 도구 러시로 승인이 창 밖으로 밀리는 것 완화).
- **m5**: Stop 훅에서 명세 기록을 승인 판정보다 먼저 수행 — 같은 턴에 명세+승인이 있을 때 `spec_presented` 유실 방지.

**반영하지 않은 것(기록)**: m1 latch 시맨틱(클릭 후 첫 훅에서 확정 — 의도된 동작으로 확정, 주석 갱신), m4 ask 경로의 APPROVED_NOTICE 부재(PreToolUse/Stop엔 주입 채널이 없는 구조적 한계 — 프로토콜 7항이 대신 안내), m6 아카이브의 질문 키 조회, m7 트랜스크립트 전체 읽기 성능(기존 훅과 동일 관례).

## 남은 것

- **재설치 dogfooding**: 채널 전환이 실사용 마찰을 실제로 줄이는지 — 특히 자명한 요청의
  체감 왕복이 "클릭 1번"으로 끝나는지, `via` 분포로 확인.
- 발산 0 판정 자체는 여전히 모델 재량(주입 프로토콜)이다. 모델이 발산을 과소 판정하면
  압축 확인이 부실해질 수 있다 — 명세 수정률 지표로 관찰.
