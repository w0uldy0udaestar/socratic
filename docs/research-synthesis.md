# mind-reader 종합 리서치 보고서

> 작성: 메인 에이전트 (Fable 5) — 서브에이전트(opus) 보고서 3건을 교차 검증·종합 | 2026-08-04
> 원본 보고서: [유사 도구·선행사례](research/similar-tools.md) · [확장 메커니즘 비교](research/agent-extension-mechanisms.md) · [질문 설계 UX](research/question-design-ux.md)

## 요약 (TL;DR)

1. **구현 방식은 훅(hooks) 기반이 유일한 답이다.** 두 보고서가 독립적으로 같은 결론에 수렴: "상시 자동 발동"을 결정론적으로 지원하는 메커니즘은 훅뿐이며, Claude Code·Codex CLI·Gemini CLI 3사가 2026년 3월부로 훅 파리티를 갖췄고 출력 스키마도 거의 동일하다. 스킬/지침 파일은 모델 재량(확률적), MCP는 발동 강제 불가 — 둘 다 보조 계층으로만 유효.
2. **시장은 붐비지만 정확히 이 조합은 비어 있다.** "질문하게 하기" 자체는 레드오션(superpowers 26만 스타, spec-kit 12.5만). 그러나 ①훅 기반 결정론적 강제 × ②답변에 따라 분기하는 적응형 질문 × ③3사 CLI 동시 지원의 교집합은 미점유. ③은 2026-03 이후에야 기술적으로 가능해진 타이밍 창.
3. **최대 리스크는 "항상 자동"의 질문 피로다.** 학술·커뮤니티·경쟁 도구 모두 과잉 질문을 경고. 해법은 리서치가 제시한 4단 게이트(탐색 우선→발산 측정→지배해석→결과성)로 "질문 0개가 정상 결과"인 설계 + 즉시 탈출구.
4. **과학적 근거가 탄탄한 설계 프로토콜을 확보했다.** 발산 측정 기반 모호성 판정(ClarifyGPT), 질문 예산 3~5(IN3/RegretBench), 가정 강등, 명세 확인의 통과 도장 방지(Vasconcelos)까지 — 프롬프트 설계의 근거 문헌이 갖춰짐.

## 교차 검증 노트 (메인 에이전트 판단)

| 쟁점 | 판정 | 근거 |
|---|---|---|
| 훅이 유일한 상시 자동 수단 | **채택 (신뢰도 높음)** | 두 보고서가 독립 조사로 일치. 확장 메커니즘 보고서는 공식 문서+소스 직접 검증, 선행사례 보고서는 경쟁 도구(prompt-improver)의 실증으로 뒷받침 |
| Codex `request_user_input` Plan 모드 전용 | **채택하되 v0.2 전 재실측** | 소스 인용(rust-v0.121.0) 근거로 신뢰도 높으나 버전 변동 가능. Codex 어댑터 설계 전 현행 소스 재확인 필요 |
| superpowers 스타 265,828 | **자릿수만 신뢰** | 2차 자료(150k)와 괴리. "10만 단위의 압도적 선두"로만 취급 |
| "항상 자동"의 위험성 | **세 보고서 모두 경고 — 설계 반영 필수** | 선행사례(HN 불만·not planned 종결), UX(RegretBench 음수 보상, CLAMBER 과잉 판정 편향), 메커니즘(주입 토큰 비용·30초 타임아웃) |
| 질문 스타일 | **선택지 + 탈출구 하이브리드** | 사용자 결정(선택지 중심)과 UX 근거(n=50 실험의 "닫혀 있음" 불만)를 종합 — 모든 질문에 선택지 2~4 + 직접입력 + "알아서" 3경로 |
| 아키네이터식 순수 정보이득 | **기각 → 정보이득×오답손실로 수정** | UX 보고서 근거(Nous 20턴, 가치 없는 비트). 원래 구상의 "아키네이터처럼"은 질문 순서 최적화(최대 분기 질문 먼저)로 번역해 반영 |

## 확정 아키텍처 방향 (토론용 권고안)

**하이브리드 5계층** (확장 메커니즘 보고서 후보 C):
- **L0 지침**: AGENTS.md + CLAUDE.md 브리지 (전 도구 폴백)
- **L1 발동**: 훅으로 매 프롬프트 가로채기 — CC `UserPromptSubmit` / Codex `UserPromptSubmit` / Gemini `BeforeAgent`
- **L2 게이트**: 명세 승인 전 쓰기 도구 차단 — `PreToolUse`/`BeforeTool` (결정론적 강제의 핵심)
- **L3 질문 UI**: 네이티브 우선(AskUserQuestion/ask_user) → 번호 평문 폴백(Codex Default)
- **L4 상태**: 세션 상태 파일(승인 플래그, 명세 저장)

**질문 프로토콜** (UX 보고서 §7): 탐색 우선 → 발산 측정(계획 3~5개 샘플링) → 가정 강등 → 예산 3~5(상한 7) 질문 루프 → 관측 가능한 종료 조건 → 통과 도장 방지형 명세 확인 → 재작성된 명세로 단일턴 실행.

## 리스크 대장

| 리스크 | 심각도 | 대응 |
|---|---|---|
| 질문 피로 → 사용자가 도구 제거 | 높음 | 4단 게이트, "질문 0개 정상", 피로 신호 즉시 중단, skip-all 탈출구 |
| 훅 지연 (CC 30초 타임아웃, 매 프롬프트 블로킹) | 높음 | 훅 스크립트는 경량 유지(주입만), 무거운 판정은 메인 모델에 위임 |
| 훅 스크립트 오류 시 fail-open → 게이트 무력화 | 중간 | 각 도구의 실패 시맨틱 명시 처리, 설치 후 self-test |
| Codex 질문 UI 부재 (Default 모드) | 중간 | 번호 평문 폴백, v0.2 전 소스 재실측 |
| 네이티브 기능에 흡수 | 중간 | 3사 동시 지원 + 프로토콜 품질(연구 기반)로 차별화, 빠른 출시 |
| 설치가 사용자 설정을 파괴 | 중간 | 병합(append) 설치, .bak 백업, uninstall.sh, --dry-run |
| 명세 확인이 통과 도장화 | 중간 | 명세 수정률을 핵심 계측 지표로, Vasconcelos식 강조 |
