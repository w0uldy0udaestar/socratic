# 질문을 통한 의도 파악 — UX·기법 리서치 보고서

> 작성: UX Researcher 서브에이전트 (opus) | 조사일 2026-08-04
> 범위: arXiv·ACL·ACM DL의 LLM 명확화 연구 20여 편, IR 검색 명확화(Bing 실데이터), HCI 과신뢰·확인 UX, 설문/챗봇 응답 부담 연구, 제품 선례(ChatGPT Deep Research, Claude Code plan mode, Spec Kit/Kiro). 2026년 6~7월 최신 논문 포함.

**한 줄 결론**: 설계 근거는 충분히 강하다. 다만 문헌이 일관되게 경고하는 실패 모드는 "모호함을 못 찾는 것"이 아니라 **"모호함을 찾고도 결과를 바꾸지 않는 질문을 던지는 것"**과 **"명세 확인 단계를 사용자가 그냥 통과시키는 것"** 두 가지. 설계의 무게중심을 여기에 둬야 한다.

---

## 0. 전제 검증 — 이 도구가 필요한가

| 발견 | 근거 |
|---|---|
| LLM은 모호한 요청에 되묻지 않고 추측한다. AmbigQA 1,000문항 × 10개 모델 평가에서 명확화 질문 비율 **5% 미만**. 판별은 되는데 행동을 안 함 | [arXiv:2605.25284, 2026-05](https://arxiv.org/html/2605.25284v1) — 사실 |
| RAG 컨텍스트를 붙이면 명확화 행동이 오히려 더 억제됨 | 위 동일 — 사실 |
| 요구사항이 여러 턴에 걸쳐 드러나면 LLM 성능 **평균 39% 하락**. 원인은 "초반 턴 성급한 가정 위에 답을 쌓고 못 되돌아오는" 패턴 | [Laban et al., arXiv:2505.06120, 2025-05](https://arxiv.org/abs/2505.06120) — 사실 |

**시사점**: mind-reader의 핵심 가치는 "질문을 잘하는 것"이 아니라 **"실행 전에 정보를 다 모아 단일턴 상태로 만드는 것"** (39% 격차 회수). 프로토콜은 "질문 → 명세 확정 → **명세를 재작성(rewrite)해서 단일턴 실행**"이어야 한다. 대화 로그를 그대로 실행에 물리면 고착 문제 재현.

## 1. 효과적인 명확화 질문 설계 기법

- **3분해 표준 프레이밍**: (a) 언제 물을지 (b) 무엇을 물을지 (c) 답을 어떻게 반영할지 — 서로 다른 실패 모드, 프롬프트 분리 필요. [Zhang & Choi, arXiv:2311.09469 / NAACL 2025 Findings](https://arxiv.org/abs/2311.09469)
- **intent-sim**: 가능한 사용자 의도들을 샘플링해 분포 엔트로피로 질문 가치 추정. 10%에만 질문 허용 시 무작위 대비 개선폭 2배.
- **자기일관성 발산 (ClarifyGPT — 가장 이식성 높은 기법)**: 같은 요구사항으로 해답 k개 샘플링 → 출력이 갈리면 모호 판정 → 갈린 지점에만 질문. GPT-4 MBPP Pass@1 70.96%→80.80%. [FSE 2024, DOI 10.1145/3660810](https://dl.acm.org/doi/10.1145/3660810). CLI 에이전트에서는 **실행 계획 k개를 샘플링해 관측 가능한 결과(변경 파일 집합, 산출물 형태, 부수효과)가 갈리는 축**을 찾으면 그대로 적용됨. "모호한가?"의 자기보고보다 훨씬 신뢰할 만함.
- **선택지 동반 질문(IN3/Mistral-Interact)**: "한 번에 한 질문 + 선택지 2~3개" 전략. 모호성 판정 85.19%, 평균 상호작용 **4.15라운드**, 라운드당 1.26개 항목(베이스라인 2.3~2.8개 몰아 묻기보다 우수), 선택지 합리성 사용자 판정 98.7%. [Qian et al., ACL 2024](https://aclanthology.org/2024.acl-long.61/) — 수치는 2차 요약 경유, 신뢰도 중간.
- **IR 실증**: Bing 명확화 패널(템플릿+슬롯+사전 정의 후보 선택)이 질의 제안 대비 상대 CTR +48%. [Zamani et al., WWW 2020](https://dl.acm.org/doi/10.1145/3366423.3380126). 클릭에 위치 편향 존재 → 권장안 1번 배치 + "권장" 라벨로 편향을 명시화.

**시사점**: ① 언제/무엇/반영 3단 분리 ② 판정은 발산 측정으로(계획 k=3~5) ③ 질문 = "무엇이 갈렸는가"의 직접 번역 ("계획 A는 기존 파일 수정, B는 새 모듈. 어느 쪽?") ④ 한 번에 하나, 선택지 2~4개, 들러리 금지.

## 2. 아키네이터식 좁히기 — 정보이득 기반 질문 선택

- 원리: 이진 질문 1개 = 최대 1비트, 최적 질문열 하한 log₂N. 매 질문마다 후보 집합을 최대한 반반으로 가르기 = 기대 정보이득 최대화. (정보이론적 사실. 아키네이터 실제 구현 세부는 공식 출처 없음 — 근거 약함)
- LLM 이식 연구: **UoT**(미래 시뮬레이션+정보이득 보상, 성공률 +38.1%, [NeurIPS 2024](https://arxiv.org/abs/2402.03271)) / **BED-LLM**(순차 베이지안 실험설계, EIG 최대 질문 채택, [Apple, arXiv:2508.21184](https://arxiv.org/abs/2508.21184)) / **Nous**(명세=이산 속성 벡터, 턴 보상=해소된 속성의 사전 엔트로피 합 — **프롬프트 내 근사 구현이 가장 쉬운 정식화**, [arXiv:2510.27410](https://arxiv.org/html/2510.27410v1))
- **주의**: 순수 정보이득은 부적합 — Nous는 20턴 사용(CLI에서 실패 수준), 정보이득은 비트를 최대화하지 가치를 최대화하지 않음("들여쓰기 2칸 vs 4칸"은 정보이득은 있으나 가치 0).

**시사점**: ① 질문 선택 기준 = **기대 정보이득 × 오답 시 손실**(되돌리기 비용 높은 축 먼저) ② **명세 슬롯을 명시적 자료구조로**: `{목표, 범위경계, 산출물형태, 대상영역, 제약, 검증방법, 하지_않을_것}` 각각 `값|후보|미정`+중요도 ③ **첫 질문은 최대 분기 질문**(교훈은 개수가 아니라 순서) ④ 답변마다 후보 계획 가지치기, 관측상 동일해지면 즉시 종료.

## 3. 질문 피로 방지

- 사용자는 질문 자체가 아니라 **쓸모없는 질문**을 싫어함: 84%가 "더 좋은 결과가 나온다면 기꺼이 답하겠다", 59%가 "짜증났다"에 비동의, 64%가 "몰입한 느낌". 가치 있는 질문 = 생각을 자극하는 질문, 단순 정보수집형은 아님. [Tix, arXiv:2407.12017](https://arxiv.org/abs/2407.12017) — 백분율 신뢰도 중간, 표본 미확인.
- 코딩 도메인: 개발자 68%가 명확화 접근 선호, 최종 코드 82%가 정밀성 기준 우수. [arXiv:2507.21285](https://arxiv.org/html/2507.21285v1)
- **적정 개수 수렴: 3~5** (IN3 실측 4.15라운드, ChatGPT Deep Research 4개, RegretBench 상위 모델 1.0~1.4턴)
- **RegretBench 경고**: 정확도 높아도 턴이 과하면 전체 보상 음수 (K2-Think V2, 74% 정확도에도 음수). [arXiv:2607.21143, 2026-07](https://arxiv.org/html/2607.21143v2)
- **선택지 vs 자유입력 (n=50, 2×2 실험)**: 선택지+AI가 명료성 최고(p<0.001), 정보량도 오히려 많음(+63자). **그러나** 신뢰성(dependability) UX 점수 하락, "너무 닫혀 있다", **"뒤로 가기 버튼이 없다"** 불만 반복. [arXiv:2506.11610](https://arxiv.org/pdf/2506.11610)
- 선택지 개수 "5~7개" Hick's law 가이드는 UX 블로그 수준 — 실측 근거는 IN3의 2~3개가 유일.

**시사점**: ① 하드 예산 기본 3~5, 상한 7, 단순 요청은 1~2 ("항상 N개" 고정 금지) ② "답이 계획을 바꾸지 않으면 묻지 말고 가정으로 표기" 명문화 ③ **하이브리드 응답 필수**: 선택지 2~4 + 직접입력 + "알아서(권장안)" ④ **되돌리기 경로**(back/skip/전부 건너뛰기) — 실측된 이탈 요인 ⑤ 진행 표시 `[질문 2/최대 4]` ⑥ 질문마다 "왜 묻는지" 한 줄 ⑦ 질문 생성 지연 금지.

## 4. 모호함 감지 기준

검증된 휴리스틱 4종:
1. **행동 발산 검사** (ClarifyGPT) — 이식성 최고
2. **의도 엔트로피** (intent-sim)
3. **슬롯 체크리스트 + 중요도** (IN3)
4. **불확실성 분해** — "모델이 모르는 것"(→탐색이 답)과 "사용자가 안 정한 것"(→질문이 답)을 분리. clarification F1 +73%. [arXiv:2606.19559, 2026-06](https://arxiv.org/abs/2606.19559). **이 구분을 안 하면 에이전트가 자기가 코드베이스를 안 읽어 생긴 무지를 사용자에게 질문으로 떠넘긴다.**

- **CLAMBER 분류**: 인식론적(Unfamiliar/Contradiction), 언어적(Lexical/Semantic), 확률적 산출(Who/When/Where/What 필수 요소 누락). ChatGPT 모호성 판별 54.25%, **모호하지 않은 것을 모호하다고 오분류하는 경향**, 질문 생성 실패의 **52.25%가 "엉뚱한 측면을 물어서"**. [ACL 2024 Findings](https://arxiv.org/html/2405.12063v2)
- **지배적 해석 규칙**: "Boston"은 99% 매사추세츠. 신뢰도 임계값만 걸면 이런 경우마다 되물어 UX 붕괴.

**판별 게이트 설계안 (순서대로)**:
```
게이트 0 (탐색 우선): 코드/파일을 읽으면 해소되는가? → 질문 대신 조사
게이트 1 (발산):     계획 3~5개 샘플링, 관측 가능한 결과가 갈리는가? → NO면 질문 안 함
게이트 2 (지배해석): 갈린 축에 관습적 기본값(저장소 기존 패턴, 표준)이 있는가? → 가정 채택+표기
게이트 3 (결과성):   틀렸을 때 되돌리기 비용이 낮은가? → 낮으면 가정하고 진행
```
+ **역-게이트**: "질문 0개로 끝내는 것이 정상적인 결과다"를 프롬프트에 명시 (과잉 모호 판정 편향 대응).

슬롯 체크리스트 (CLAMBER AO × IN3 중요도의 CLI 번역): 대상 범위(Where) / 산출물 형태(What) / 성공 기준·검증 / 범위 경계(하지 않을 것) / 제약(호환·의존성) / 사용자·공개 범위(Who) / 용어 해석("정리해줘"=삭제? 재구성? 문서화?).

## 5. 종료 조건

정지 규칙(OR, 전부 관측 가능한 양으로):
1. **수렴(주 조건)**: 남은 후보 계획들이 더 이상 관측 가능하게 갈리지 않음 — 자기보고 확신도보다 신뢰할 만함
2. **슬롯 충족**: 중요도 '상' 슬롯 전부 확정 또는 명시적 가정
3. **한계효용 소진**: "물어서 얻는 것보다 만들어 보여주고 고치는 게 빠른가?" → 빠르면 종료
4. **예산 소진**: 권장 5, 하드 7
5. **사용자 피로 신호 즉시 중단**: 명시("그냥 해", "알아서"), 암묵(답변 급격히 짧아짐, 응답 지연 급증), 조작(skip all) → 다음 질문 없이 명세 확인으로 직행, 미정 슬롯은 기본값+'가정' 라벨
6. **비대칭 규칙**: 되돌리기 어려운 작업(삭제·덮어쓰기·배포·스키마 변경)은 예산 무관하게 해당 축 반드시 확인

**핵심 설계 결정**: 미해결 슬롯을 침묵 기본값 처리 금지. **질문을 줄이는 진짜 방법은 질문을 "확인 가능한 가정"으로 강등하는 것.**

## 6. 명세 확인 단계 UX — 통과 도장(rubber stamp) 방지

**나쁜 소식(사실)**: "AI는 자주 틀린다"고 고지하고 오류를 찾으라고 지시해도 치명적 결함을 자주 놓침([arXiv:2508.06484](https://arxiv.org/pdf/2508.06484)). AI 뉴스 요약의 45%가 유의미한 오류(EBU/BBC, 신뢰도 중간). 직원 66%가 검증 없이 신뢰(KPMG, 신뢰도 중간). → **"예쁘게 보여주고 y/n"은 거의 확실히 통과 도장이 된다.**

**검증된 개입**:
| 개입 | 효과 | 출처 |
|---|---|---|
| 인지적 강제 함수 (스스로 판단 먼저, 요청 시 공개, 지연) | 과신뢰 유의 감소. 단 주관 만족도는 하락 → 하나만 쓸 것 | [Buçinca et al., CSCW 2021](https://arxiv.org/pdf/2102.09692) |
| **"수정될 확률 높은 토큰" 하이라이팅** | 더 빠르고 표적화된 편집, 선호됨 | [Vasconcelos et al., TOCHI 2024](https://dl.acm.org/doi/abs/10.1145/3702320) |
| "생성 확률 낮은(불확실한) 토큰" 하이라이팅 | **효과 없음** | 위 동일 |

**Vasconcelos 원리 = 핵심**: "내가 확신 없는 부분"이 아니라 **"당신이 다르게 생각할 가능성이 높은 부분"**을 강조하라.

**명세 확인 화면 설계안**:
1. 한 눈 분량(스크롤 없이). 긴 명세 = 통과 도장.
2. 항목별 출처 표시: `✓ 당신이 답한 것 / ~ 내가 가정한 것 ← 여기를 보세요 / ? 아직 안 정한 것`
3. "사용자가 수정할 확률이 가장 높은 항목 2개"를 상단 별도 섹션으로
4. **하지 않을 것(out of scope) 명시** — 누락은 눈에 안 보이므로 적극 언어화
5. 인지적 강제 함수 하나만: "이 중 틀린 것이 있으면 번호 입력, 없으면 Enter" (틀린 것 찾기 과제로 프레이밍)
6. 실행 후 첫 관측 가능 결과 예고: 변경 파일 / 새로 생기는 것 / 검증 명령
7. 명세를 파일로 저장 (`.mind-reader/spec-<id>.md`) — 실행 후 대조·진단 가능
8. EARS 정형 문법은 고려하되 강제 금지 (CLI 가독성, 추정)

## 7. 종합 프로토콜 초안

```
[0] 탐색 우선 게이트 → 읽어서 해소되면 질문 아님
[1] 발산 측정: 계획 3~5개 샘플링 → 차이축 추출. 차이 없음 → 질문 0개, 명세 확인으로
[2] 축 필터링: 관습 기본값? 되돌리기 저비용? → '가정' 강등
[3] 우선순위: (기대 정보이득 × 오답 손실) 정렬, 최대 분기 질문 1번
[4] 질문 루프 (예산 3~5, 상한 7): 한 번에 하나, 선택지 2~4 + 직접입력 + "알아서",
    이유 한 줄, [n/최대] 표시, back/skip/skip-all. 매 답변 후 가지치기 → [1] 재평가
[5] 종료 판정 (OR): 수렴 | 슬롯 충족 | 한계효용 | 예산 | 피로 신호 | (위험 작업은 반드시 확인)
[6] 명세 확인: 한 눈 분량, 출처 표시, 수정 확률 높은 항목 상단, out-of-scope 명시,
    가정만 개별 확인, 변경 파일+검증 예고
[7] 실행: 대화 로그가 아니라 재작성된 명세로 단일턴 실행 (39% 하락 회피)
```

**흔한 실패 모드 3개와 대응**: ① 엉뚱한 걸 묻는다(실패의 52.25%) → 발산 측정으로 축을 데이터에서 추출 ② 너무 많이 묻는다 → 예산 + 가정 강등 ③ 명세를 안 읽고 승인한다 → 짧게 + 출처 표시 + 가정만 개별 확인.

## 8. 한계와 공백

- IN3 수치(4.15라운드 등)는 2차 요약 경유 — 원문 재확인 권장
- Tix 백분율은 표본 크기 미확인 — 방향성 근거로만
- 선택지 최적 개수의 대규모 실측 근거 없음 — 자체 A/B 필요 (2 vs 3 vs 5)
- CLI 환경 명확화 UX 직접 연구 없음 — 웹/챗봇/IDE 근거의 터미널 이식은 추정
- read-back "오류 40% 감소" 류 수치는 출처 추적 실패 — 인용 금지
- **계측 지표 제안**: "명세 수정률" — 사용자가 명세를 실제로 수정하는 비율. 0에 가까우면 확인 단계가 작동하지 않는 것. 이 도구의 성공/실패를 가르는 단일 지표 후보. RegretBench 평가 프레임(정확도+효율+질문 근거성+regret)을 자체 평가 하네스로 차용 권장.
