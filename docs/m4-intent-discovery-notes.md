# M4 의도 발견 프로토콜 — 설계 노트

> 시작: 2026-08-10 | 브랜치 `feature/m4-intent-discovery` | 결정 D17

## 요약

M3 재설치 dogfooding에서 승인 채널 마찰(D15·D16)은 해소됐으나, socratic이 "작업을 맡기면 그냥 이게 맞냐 확인하는 정도의 역할"로 퇴화한 것이 드러났다. M4는 프로토콜을 **확인 게이트에서 아키네이터식 의도 발견 루프로** 재정의한다: 발산 측정의 대상을 '실행 계획'에서 '결과물 그림'으로 바꾸고, 확신이 서기 전에는 명세 제시를 금지하며, 질문 억제 문구("질문 0개는 정상 결과")를 모호도 비례 원칙으로 교체했다. 1단계는 텍스트 개정 + dogfooding 측정, 부족하면 2단계로 훅 강제를 추가한다.

## 사용자 교정 (2026-08-10, M3 dogfooding 직후)

> "지금 설치해서 사용해보니까 작업을 맡기면, 그냥 이게 맞냐 확인하는 정도의 역할밖에 못하고 있어. 내가 원하는 건 — 아키네이터가 여러 질문으로 상대가 생각하는 한 단어를 알아내듯, socratic은 질문을 계속해서 내 의도와 생각을 알아내는 거지."

핵심 통찰: **M2 제거의 원인이었던 마찰은 승인 채널의 마찰이었지 질문 자체가 아니다.** 사용자의 1순위는 여전히 "얼렁뚱땅 넘어가지 않는 것"(D9)이고, 좋은 질문은 마찰이 아니라 제품의 핵심 가치다. M3가 마찰을 줄이면서 질문 루프까지 눌러버린 것이 문제였다. PLAN.md 1절의 확정 정의("생각이 정확한 언어가 될 때까지 다양한 각도로 질문을 파고들게 강제")는 처음부터 발견 엔진을 가리키고 있었다.

## 퇴화의 원인 진단 (구 프로토콜)

1. **발산 측정 기준이 '실행 계획'** (구 2항) — "실행 계획을 3~5개 상상해 관측 가능한 결과가 갈리는 축을 찾아라." 대부분의 위임형 요청은 실행 방법이 자명하므로 모델이 쉽게 "발산 없음"을 판정했다. 그러나 실행이 자명해도 사용자 머릿속 그림(목적·형태·기준·취향·제약)은 갈라져 있을 수 있다.
2. **"질문 0개는 정상 결과다" 명시** (구 2항) — 과잉 질문 편향 대응으로 넣은 문구가, 질문 최소화 편향이 있는 모델에게 상시 탈출구로 작동했다.
3. **가정 강등(구 3항)이 남은 질문마저 제거** → D16 압축 확인이 사실상 기본 경로가 되어, 매 요청이 "재진술 + 승인/수정 선택창 1개"로 끝났다.

## 설계 결정 (2026-08-10 사용자 선택, 4항목 모두 권장안)

| 축 | 결정 | 내용 |
|---|---|---|
| 질문 대상 | **의도 전체 탐구** | 실행 갈림만이 아니라 목적·형태·기준·취향·제약 — 계획이 안 바뀌어도 이해를 재우는 질문 허용 |
| 자명한 지시 | **모호도 비례** | 명시된 것은 절대 되묻지 않음(D16 유지). 모호할수록 질문 라운드가 깊어짐. 압축 확인 직행은 갈림이 전혀 없는 완전 자명한 지시만 |
| 종료 조건 | **확신 수렴 + 사용자 판정** | 라운드마다 "명세를 쓰면 '정확히 그거'라고 할 확신"을 재평가. 확신 전 명세 제시 금지. 최종 판정은 사용자(D9 유지) |
| 강제 수단 | **프로토콜 개정부터** | 1단계 텍스트 개정 → dogfooding 측정 → 부족하면 2단계 훅 강제(질문 0회 명세 제시 차단) |

## 프로토콜 개정 내역 (`src/protocol.ts`)

| 항 | 구 (M3) | 신 (M4) |
|---|---|---|
| 서두 | "아래 절차를 따르라" | 정체성 문장 추가: "너는 실행자이기 전에 질문자다. 아키네이터가 …좁혀가듯 사용자의 머릿속 그림을 알아내라. 확인 도장이 아니라 발견이 목적이다" |
| 1) 탐색 우선 | "질문은 사용자만 아는 것에만" | 사용자만 아는 것의 목록을 명시: 목적·결과의 모습·좋음/완료 기준·취향·하지 말 것 |
| 2) 발산 측정 | 실행 계획 3~5개, 갈리지 않으면 "질문 0개는 정상 결과" | **그림 발산 측정**: 요청을 만족한다고 주장할 수 있는 결과물 3~5개. "실행 방법이 자명해 보여도 그림이 갈리면 모호한 것이다." 질문 0개 문구 삭제 |
| 3) 가정 강등 | 강등 후 바로 질문 루프 | **모호도 비례**로 확장: 명시된 것 되묻기 금지 + 완전 자명한 지시만 압축 확인 직행 |
| 4) 질문 루프 | 정렬 기준 (결과를 가르는 정도 × 되돌리기 비용) | 정렬 기준 "그림을 가장 크게 좁히는 것부터" + 라운드마다 갱신(좁힌 것·새 갈림·미지). 각도 전환 3단은 유지 |
| 5) 종료 | "의도가 파악될 때까지 계속" | **확신 수렴**: 라운드마다 자문, 확신 전 명세 제시 금지. 질문 가치 기준을 "계획이 달라지는"에서 "그림을 좁히는"으로 |
| 6) 확인·승인 | "발산 없음(질문 0개)" 경로 | "완전 자명(3에서 직행)" 경로로 개명. 명세 구성에 '목적' 항목 추가. D15 승인 채널·[MR-SPEC]·'승인' 라벨 등 기계적 마커는 전부 불변 |
| 7) 승인 처리 | — | 변경 없음 |

훅 코드(`common.ts`·`filter.ts`·훅 3종)는 건드리지 않았다 — 승인 판독이 의존하는 마커([MR-SPEC], '승인' 라벨, AskUserQuestion 모양 검증)가 그대로이기 때문이다.

## 프롬프트 리뷰 반영 (2026-08-10, Prompt Engineer 에이전트 — 훅 코드 교차 대조)

개정 직후 리뷰에서 탈출구 헌팅을 수행, 상 3건·중 2건을 전부 반영했다. 핵심 발견: **"질문 0개는 정상 결과"를 지웠어도 가정 강등(3항)이 판정자 재량 + 흔적 미표시 조합으로 동일한 퇴화 경로를 재현할 수 있다.**

| # | 발견 | 반영 |
|---|---|---|
| 상-1 | 가정 강등 기준("관례로 정해짐", "고치기 쌈")이 무한 확장 가능한 새 주력 탈출구 | 강등 허용 범위를 "어느 그림을 골라도 '정확히 그거'라고 할 세부"로 한정, 목적·형태·기준·취향 축은 강등 금지 명시 |
| 상-2 | 압축 확인 경로에 가정 표시 의무가 없어 강등 남용을 은닉 가능 | "강등한 가정은 재진술에 각각 한 줄로 명시, 가정을 숨긴 압축 확인은 무효" 추가 |
| 상-3 | 0항 "자명한 후속 지시면 재시작하지 말라"가 훅 동작과 모순 — 승인 후 실질 발화는 항상 새 사이클(`filter.ts` `startsNewCycle`)이라 텍스트를 따르면 게이트 차단에 부딪힘 | "승인된 작업의 후속 지시면 파악한 그림을 재사용해 압축 확인으로 짧게 재승인"으로 현실 정렬 |
| 중-4 | "알아서 해" 시 "축 1~2개 압축 확인"이 별도 질문 라운드로 읽힐 수 있음 — M2 마찰 재발 위험 | "즉시 6)으로, 미해결 축은 내 선택을 담아 가정 목록 맨 위에, 별도 질문 라운드 금지"로 명확화 |
| 중-5 | 직행 조건 "완전히 자명한 지시"가 성질 서술이라 강등 분석 생략 선언 가능(역방향: 과잉 교정) | "강등을 마친 뒤 갈림이 하나도 남지 않을 때만 직행"으로 절차 출력화 |
| 하-7 | 파일 주석 "매 실질 프롬프트마다 주입"이 구현과 불일치 — 실제는 사이클 시작 1회(`prompt-submit.ts`) | 주석 수정 |

기계적 마커([MR-SPEC]·'승인' 라벨·AskUserQuestion)는 훅 파싱 코드(`common.ts`·`filter.ts`)와 대조해 이상 없음 확정. 잔여 리스크: 강등 남용은 소프트 계층이라 완전 차단 불가 — stats의 사이클당 질문 수 분포로 퇴화 재발을 조기 감지한다(아래 검증 계획).

## 검증 계획 (dogfooding 관찰 포인트)

- **질문 라운드 수 분포** — 모호한 위임형 요청에서 0라운드가 지배적이면 개정 실패. 자명한 지시가 여전히 1왕복이면 D16 유지 성공.
- **명세 수정률** — 0에 가까우면 확인 도장화 신호(질문이 그림을 못 좁히고 있다는 뜻). 기존 지표 그대로.
- **질문 품질 체감** — 답을 이미 아는 질문·결과가 같은 질문이 나오는지. 나오면 가치 밀도 문구 보강.
- 1단계로 부족하면 2단계: 훅이 트랜스크립트에서 AskUserQuestion 라운드 수를 세어, 프롬프트 필터가 '실질 요청'으로 판정한 사이클에서 질문 0회로 [MR-SPEC]을 제시하면 Stop/PreToolUse에서 차단. (프롬프트 필터의 오탐이 곧 차단 오탐이 되므로, 도입 전 오탐률 실측 필요.)
